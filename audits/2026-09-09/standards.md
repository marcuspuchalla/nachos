**Standards scope and extension roadmap**

CBOR has a stable base format and independently specified extensions and application profiles. [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html) supersedes RFC 7049 without introducing a new wire-format version. Cardano serialization is defined by ledger specifications and CIPs; it is not an alternative IETF CBOR RFC edition. TACO should express these as separate profiles and publish support for each.

The implementation was audited against the core specification, its public API promises, and the cited Cardano structures. The extension rows below are a **support inventory and implementation roadmap**, not a claim that every clause of every listed application protocol was audited. Current source has generic tag wrapping and a limited switch of validators/converters; a named enum or friendly label does not demonstrate semantic support.

| Specification / profile | Current Nachos assessment | Recommended scope and tests |
| --- | --- | --- |
| [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html) core, including malformed examples and diagnostic notation | Broad implementation with the concrete N01–N12 gaps | Repair core first; test every entry point against the same requirements and preserve original CBOR types |
| [RFC 7049](https://www.rfc-editor.org/rfc/rfc7049) compatibility and length-first ordering | `mapKeyOrder:'length-first'` is the documented default; `bytewise` also exists | Name both ordering profiles explicitly; cross-check emitted and validated order on mixed-type keys |
| [RFC 8742](https://www.rfc-editor.org/rfc/rfc8742.html) CBOR Sequences | Buffered `parseSequence` and `parseSequenceWithSourceMap` exist | Add aggregate-limit/deadline and source-map parity tests; incremental input/resume is separate work |
| [RFC 8746](https://www.rfc-editor.org/rfc/rfc8746.html) typed/multidimensional arrays | Generic tag preservation; no dedicated typed-array/dimension semantics | Implement registered typed-array tags in 64–87 and array tags 40/41/1040; test endianness, element widths, alignment, dimensions, and malformed payloads |
| [RFC 8943](https://datatracker.ietf.org/doc/rfc8943/) date tags 100/1004 | Opaque tags | Add exact day/date representations and calendar validation, independent of JavaScript Date's range |
| [RFC 9581](https://datatracker.ietf.org/doc/rfc9581/) time/duration/period tags 1001–1003 | Opaque tags | Add map/content validation, exact subsecond values, and timescale-aware interpretation; avoid silently coercing everything to Date |
| [RFC 9090](https://www.rfc-editor.org/rfc/rfc9090.html) object identifier tags 110–112 | Opaque tags | Implement OID/relative OID decoding and payload validation; add compact encoding and malformed subidentifier vectors |
| [RFC 9164](https://www.rfc-editor.org/rfc/rfc9164.html) IP address/prefix tags 52/54; legacy 260/261 | Opaque tags | Add byte lengths, address/prefix/range distinctions, and boundary tests; identify legacy encodings explicitly |
| [RFC 9277](https://www.rfc-editor.org/rfc/rfc9277.html) stored CBOR identification | Opaque tags | Recognize file/sequence identification and protocol-specific magic; test the whole envelope rather than merely accepting its tag |
| [RFC 9485](https://www.rfc-editor.org/rfc/rfc9485.html) I-Regexp / tag 21065 | Opaque tag; legacy tag 35 only checks text | Validate the advertised pattern syntax in an optional module. Generic inspection should not execute user-provided regular expressions |
| [RFC 9542](https://www.rfc-editor.org/rfc/rfc9542.html) IEEE identifiers / tags 48,1048 | Opaque tags | Add identifier shape/length checks and readable display |
| [RFC 8610](https://www.rfc-editor.org/rfc/rfc8610.html), [RFC 9165](https://www.rfc-editor.org/info/rfc9165/), [RFC 9682](https://www.rfc-editor.org/rfc/rfc9682.html) CDDL | No schema engine; partial extended diagnostic parsing | Use a separate schema validator for application profiles and generation. CDDL support is not required to decode CBOR bytes |
| [COSE RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html), [CWT RFC 8392](https://www.rfc-editor.org/rfc/rfc8392.html), [PoP RFC 8747](https://www.rfc-editor.org/rfc/rfc8747.html), [countersignatures RFC 9338](https://www.rfc-editor.org/rfc/rfc9338.html) | Opaque containers; no complete protocol validator | Add structural profiles and public fixtures. Report cryptographic verification independently; decoding a signature container does not verify its signature |
| [RFC 9254](https://www.rfc-editor.org/rfc/rfc9254.html) YANG-CBOR, [RFC 9290](https://www.rfc-editor.org/rfc/rfc9290.html) problem details | Opaque tags/maps | Optional domain modules once their users and schemas justify them; do not inflate core-CBOR scores with these |
| [RFC 9711](https://www.rfc-editor.org/rfc/rfc9711.html) EAT and [RFC 9781](https://www.rfc-editor.org/info/rfc9781/) UCCS | Opaque tags/maps | Optional structural/claim profiles; distinguish protected, unprotected, and verified data |
| Registered non-RFC extensions, including shared values 28/29, string references 25/256, rational 30, UUID 37, set 258, map 259 | Generic wrapping; set uniqueness has the same comparison defects as maps | Implement modules against each registration's actual specification. Shared values require graph-aware semantics and resource limits; do not confuse generic tag acceptance with dereferencing support |
| [DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/) | No named validating profile | Test its restrictions and link representation separately. A DAG-only decoder's rejection of general CBOR can be correct for its documented scope |
| Cardano ledger profiles | Helpers and era detection; partial semantic validation | Pin per-era CDDL and binary implementation revisions. Test Byron and Shelley-family envelopes separately, and treat post-Conway source evolution as versioned future scope rather than assuming mainnet activation |
| [CIP-21](https://cips.cardano.org/cip/CIP-0021) hardware-wallet profile | Ordering flag and generic strict bundle only | Validate the actual interoperability restrictions, including transaction-wide set-tag consistency, without treating them as universal ledger validity |
| [CIP-19](https://cips.cardano.org/cip/CIP-0019), [CIP-25](https://cips.cardano.org/cip/CIP-0025), [CIP-68](https://cips.cardano.org/cip/CIP-0068) | Address and CIP-25 helpers; no complete CIP-68 profile | Test each helper independently from CBOR syntax. Use v1/v2 metadata and byte/text-key cases; distinguish plausible era inference from validated era membership |
| [CIP-114](https://cips.cardano.org/cip/CIP-0114) Cardano tag registry | No generated registry support | Track its **Proposed** status and pin referenced tag definitions; it is not itself proof that every proposed structure is deployed |
| [CDE draft-13](https://datatracker.ietf.org/doc/draft-ietf-cbor-cde/) and [diagnostic notation draft-27](https://datatracker.ietf.org/doc/draft-ietf-cbor-edn-literals/) | No declared versioned draft profiles | At retrieval CDE-13 is expired/parked; the diagnostic draft is active and titled Concise Diagnostic Notation. Keep experimental targets pinned and separate from RFC support claims |

The [IANA CBOR tag registry](https://www.iana.org/assignments/cbor-tags) was retrieved on 2026-09-09; its XML `updated` date is 2026-07-20. The main tag table contains **351 records including ranges and unassigned entries**, not 351 individually implemented features. [iana-rfc-index.json](iana-rfc-index.json) records all 19 distinct RFC references in that main table, including domain-specific RFC 9132 and RFC 9393 beyond the immediate module roadmap. Time-map keys and timescales are deliberately excluded from the tag-number count.

A registry snapshot is not an exhaustive list of every RFC using CBOR. Sequences, schemas, profiles, tag-registration references outside RFCs, and future assignments need separate catalogs. Maintain a generated registry index with reference/status metadata and a hand-reviewed implementation matrix. Updating tag names can be routine; implementing semantics requires dedicated tests.

The [RFC 8949 errata service](https://www.rfc-editor.org/errata/rfc8949) initially failed through the browser tool; direct retrieval subsequently succeeded. It listed one verified technical correction: [erratum 8589](https://www.rfc-editor.org/errata/eid8589), verified 2025-11-07, clarifies that equivalent NaN map keys must also have matching sign bits. The N05-nan-sign probe reproduces rejection of opposite-sign NaN keys as duplicates. Preserve NaN representation in the lossless model and implement the specified equivalence; JavaScript Map alone cannot retain that distinction. Pin this verified correction in the oracle metadata. Reported or rejected errata should not silently redefine requirements.

The best path toward comprehensive support is: **correct and lossless core → reliable TACO oracle → exact numeric/embedded/tag modules → useful registered extensions → named application/schema profiles**. This sequence lets every expansion produce a defensible coverage increase instead of a larger list of accepted tag numbers.
