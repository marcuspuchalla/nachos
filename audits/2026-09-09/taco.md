**TACO findings and coverage plan**

TACO already has a valuable architecture: language-isolated HTTP adapters, a common vector corpus, negative cases, report generation, and a recent attempt to distinguish bridge errors from library behavior. Its current results still cannot measure comprehensive standards support accurately.

The configured Docker matrix has **19 implementations across 10 languages**. The current corpus has **355 vectors: 152 core, 137 Cardano, and 66 edge cases**, rather than the README's 358. Only 36 vectors have `rfcSection`, and one of those is a descriptive phrase rather than a section. Four have a `cip` field. The corpus has no structured fixture-origin, ledger-revision, requirement-ID, or expected-profile schema. A dependency in the root package manifest or an adapter in `examples/` does not mean that implementation runs in the Docker matrix.

| ID / priority | Evidence | Proposed change |
| --- | --- | --- |
| T01 / P1 | [runner.js](../../../taco/docker/runner/runner.js) makes byte markers equal to hex strings, numbers equal to numeric text, -0 equal to +0, and differently numbered unknown tags equal through unwrapping. [PROTOCOL.md](../../../taco/docker/PROTOCOL.md) requires map-key stringification; the Nachos adapter turns `{1:"integer", "1":"text"}` into a single JSON property. All are reproduced by the audit. | Use a typed bridge representation for every CBOR value. Maps must be entry arrays with typed keys. Integers and uint64 tags need decimal strings inside explicit type records; floats need signed-zero/nonfinite handling and optional wire bits; unassigned simple values need their own type. Treat approved semantic projections separately from lossless comparison. |
| T02 / P1 | After a correct decode, the runner marks an encoder returning `ff` as passing. It checks only for a nonempty encoded string, with a weak inequality check on noncanonical cases. It never validates or decodes the encoded output for equivalence. | Independently validate encoder output and compare its decoded typed value. Add encoder-input vectors independent of the decoder. Report decode, encode, semantic round-trip, byte-preserving round-trip, and deterministic output as distinct capabilities. |
| T03 / P1 | `anyOf:[{success:false}]` accepts `TypeError: broken adapter` as a successful rejection before error classification. Other negative cases count `unsupported` as an acceptable rejection. | Classify transport, adapter, unsupported-feature, resource-limit, malformed-CBOR, and validity failures before matching outcomes. Declare allowed rejection classes; use structured adapter error codes rather than English regexes. |
| T04 / P1 | Every ordinary successful decode is followed by mandatory encoding; decode-only implementations are penalized. `profile:"strict"` is a score label, not a decoder configuration: requests contain only hex. Some `anyOf` paths return before encoder testing. | Introduce explicit operations and profiles, negotiate adapter capabilities, and send profile options. A library can pass decoding while lacking encoding. A generic pass-through result must not imply semantic validation. |
| T05 / P1 | Running all three generators in a temporary copy changes 12 files, reduces transaction cases from 21 to 9, removes all 10 `anyOf` fields, and produces 41 lint errors. Numeric NaN/Infinity expectations serialize through ordinary JSON. `npm run generate-tests` only runs the core generator. | Make a single versioned schema and generator entry point authoritative. Encode special values explicitly. Either generate the entire corpus deterministically or label maintained fixtures as handwritten. CI should regenerate in a temporary directory and require a clean comparison. |
| T06 / P1 | Two current vectors still disagree with the bridge/CBOR semantics: `tx-body-field-voting-procedures` expects a comma-string key instead of the documented structured-key serialization, and `malformed-tag-2-invalid-content` expects `"0"` for tag 2 over integer 1. | Fix the oracle using primary specs and independently checked bytes. For tag 2 over the wrong content type, test opaque preservation separately from semantic rejection; do not invent a numeric value. Add typed structured-key fixtures. |
| T07 / P1 | The Nachos container still requests `^0.3.0` and hardcodes health version `0.3.0`. Node Dockerfiles copy only package.json and run npm install, ignoring available lockfiles. Health checks discard version details. Report provenance contains Git HEAD but not the dirty diff/corpus/artifact identity. | Pin exact package/image/toolchain versions; install from locks or the reviewed tarball. Record actual runtime library versions, package integrity, image digest, adapter hash, corpus hash, options, runtime, and source state in each report. |
| T08 / P1 | `main().catch(console.error)` can finish with exit code 0 after an exception; healthy-library subsets can continue; `--abort-on-container-exit` does not identify the runner as the authoritative result. Adapter-invalid reports and bridge-error exclusions can leave misleading headline percentages. | Set a failing runner exit code on infrastructure or fixture failure, require the expected matrix unless explicitly running a subset, use `--exit-code-from test-runner`, and publish explicit tested/untested denominators. Competitor conformance failures should be findings, not infrastructure failures. |
| T09 / P2 | Containers and test cases are traversed serially in the runner. Root TypeScript and Docker runner schemas/comparators have diverged. Existing saved rankings predate the new runner and lack its provenance field. | Use a bounded CI matrix over libraries, consolidate shared types and comparison rules, test the runner itself, and regenerate results only after the scoring repairs. Preserve historical reports with their own corpus/version identities. |

The runtime audit loaded the **actual current** `docker/runner/runner.js` and Nachos `server.js` functions without starting HTTP servers, then supplied an in-memory transport. Running all 355 current vectors produced 352 passes, the two oracle mismatches above, and rejection of the separately labeled 500-depth stress case. This explains current behavior but is not a Docker benchmark. The runner's demonstrated false positives make “352/355” unsuitable as a coverage claim. Full raw observations are in [observations.json](observations.json).

The vector linter is useful for syntax and well-formedness, but cannot certify expected semantics, sufficient assertions, or complete standards coverage. The [generator evidence](generator-observations.json) also shows why its current green result is not enough to trust regeneration.

**A coverage model worth publishing**

Represent a requirement with `id`, specification URL/revision/section, feature, layer, operation, profile, allowed outcomes, and fixture provenance. Separate mandatory core behavior from extensions. Each implementation row should expose preservation, interpretation, validity checking, encoding, deterministic mode, and resource limits.

| Coverage track | Cases to add or strengthen | Oracle |
| --- | --- | --- |
| Core syntax and validity | Every initial-byte family; truncation at every byte boundary; reserved AI; missing/misplaced breaks; string chunk type restrictions; UTF-8 invalid sequences and BOM; duplicate keys with structurally complex keys | [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html), [CBOR test-vectors](https://github.com/cbor/test-vectors), independent scanner plus hand-checked expectations |
| Numbers | Integer boundaries through ±2^64; tagged bignums; integral floats vs integers; signed zero; all finite binary16 patterns; NaN/infinity and width boundaries | Independent numeric/bit oracle; exact type/value comparisons |
| Deterministic profiles | Preferred widths for every major type, nested maps, tagged maps, both key orders, no indefinite items, preservation metadata overrides, profile-specific numeric choices | Named [core/length-first requirements](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2) with expected bytes |
| Sequences and streaming | Empty sequence, multiple items, truncated last item, all input splits, partial-read resumption, total deadlines/limits | [RFC 8742](https://www.rfc-editor.org/rfc/rfc8742.html); treat “need more input” separately from rejection |
| Optional extensions | Every supported tag's valid and invalid payloads; nested use; raw preservation, interpreted value, and validation scored separately | Per-tag specification from [standards.md](standards.md) |
| Cardano serialization | Era-specific transaction envelopes, body/witness sets, redeemer arrays/maps, inline datums, reference scripts, voting/proposals, certificates, constructor boundaries 6/7/127/128, large constructor indices, byte chunks of 0/64/65 bytes | Pinned [ledger CDDL and binary implementation](https://github.com/IntersectMBO/cardano-ledger), independent Cardano decoders, published CIP fixtures |
| Cardano application profiles | CIP-19 addresses; CIP-25 v1/v2 metadata; CIP-68 datum metadata; hardware-wallet CIP-21 constraints; minimum-era evidence | Named CIP/era profiles; generic CBOR acceptance cannot establish these |
| Real deployments | Public transaction/UTXO/datum/metadata bytes with network, transaction/block ID, era, source URL, retrieval date, byte hash, and expected interpretation | Verified upstream fixtures or public chain data checked by at least two independent implementations |
| Robustness | Depth/width/chunk counts, huge declared lengths with tiny input, shared references, source-map work, timeouts, cancellation | Resource-budget checks separate from conformance; retain minimized regression cases from fuzzing |

The app contains scraped fixture files, but its ordinary test suite does not consume those batches. Move verified samples into a versioned shared corpus after checking their completeness and provenance. Synthetic transactions are still useful; label them synthetic and distinguish structural examples from ledger-valid transactions. A transaction hash must come from the original ledger-defined byte slice, not an arbitrary re-encoding.

For realistic extension fixtures, include [COSE examples](https://github.com/cose-wg/Examples), CWT tokens, WebAuthn/CTAP objects, SenML records, and DAG-CBOR objects. These should have their own requirements and claims; structural decoding must not be labeled signature verification or full protocol compliance.

Publish requirement coverage with its denominator, for example “all vectors for 18/20 tested core requirements passed”, alongside `partial`, `unsupported`, `not tested`, and `adapter invalid`. An unsupported optional profile should lower the breadth measure, not silently disappear from it. Infrastructure errors should block ranking that row until repaired; excluding difficult cases and sorting by the remaining percentage can reward broken adapters. Keep per-feature drill-down to exact vectors and pinned sources. Do not announce an overall winner until every compared row uses the same reviewed corpus and profiles.
