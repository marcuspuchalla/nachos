**Nachos findings and proposed remediation**

These findings apply to the current working-tree 0.4.0 candidate, including the earlier July remediation. P1 means address before rollout; P2 means a completeness or API improvement to scope explicitly. Each `Nxx` corresponds to reproducible checks in [probe.mjs](probe.mjs) and [observations.json](observations.json). Optional extension handling and lossless-editing promises are distinguished from CBOR wire errors.

| ID / priority | Finding and reproduction | Cause and proposed change |
| --- | --- | --- |
| N01 / P1 | `decode('5f')`, `decode('7f')`, `decode('5f4101')`, and `decode('7f6161')` succeed even though the terminating break is absent. Hex, byte input, and source-map paths all reproduce. | In [useCborString.ts](../../src/parser/composables/useCborString.ts), the chunk loop ends at EOF and returns success without recording a break. Require an observed terminator, including empty and nested strings. |
| N02 / P1 | `decode('63efbbbf').value` is `""`; the encoded U+FEFF disappears. | `new TextDecoder('utf-8')` consumes the initial BOM. Preserve it with the appropriate decoder option and test definite strings and each indefinite chunk. This changes actual text content, independently of invalid-UTF-8 policy. |
| N03 / P1 | `c24101` throws under `validateTagSemantics:true`; valid decimal `c48200c249010000000000000000` fails too. `c482f9000001` incorrectly accepts a float exponent. `c25f420100ff` bypasses a one-byte bignum limit. | [useCborTag.ts](../../src/parser/composables/useCborTag.ts) and the source-map tag parser convert bytes to BigInt before validating the required content type. Chunk wrappers miss the conversion/limit branch. Validate raw CBOR types first, support byte wrappers, then interpret exact numeric values. Preserve original representation separately. |
| N04 / P1 | Source maps accept `980100` and unordered `a202000100` with `validateCanonical:true`; normal decode rejects them. Source maps ignore `allowTrailingData:false` for `0102` and `unwrapSelfDescribed:true` for `d9d9f701`. | [useCborParser.ts](../../src/parser/composables/useCborParser.ts) duplicates collection parsing and omits shared validation/postprocessing. Refactor to one scanner with optional source events, and run identical option/input tests across entry points. |
| N04 / P1, lossless/UI | `a201010102` re-encodes unchanged after normal decode but becomes `a10102` after source-map decode. Mixed keys in `a20100613101` receive colliding `.1` value paths. Indefinite-map keys also share a repeated `#key` path. | Source-map maps omit retained entries/indefinite metadata and identify values using stringified keys. Use stable entry/node IDs, distinct key/value roles, and original-entry storage. Duplicate-key acceptance is a policy choice; lossless editing must not silently discard accepted bytes. |
| N05 / P1 | Distinct map keys in `a2a1010100a1010201` are reported as duplicates. Arrays `["a,str:b"]` and `["a","b"]` collide. Conversely, `a26161007f6161ff01` accepts two equal text keys under duplicate rejection. | [serializeValueForComparison](../../src/parser/utils.ts) treats every native Map as an empty object, uses unescaped delimiters for arrays, and compares string wrappers structurally. Implement CBOR-aware structural equality with an explicit numeric-equivalence policy and normalized string content; use the same logic for set uniqueness. |
| N06 / P1 | `fa3fc00000` (binary32 1.5) passes deterministic validation despite fitting binary16. Exhaustive widening gives 63,406 incorrect acceptances out of 63,488 finite patterns. | [useCborFloat.ts](../../src/parser/composables/useCborFloat.ts), `fitsInFloat16`, shifts a JavaScript Number by 42; Number bitwise operators truncate to 32 bits and mask the shift count. Use correct BigInt bit extraction or an independently verified exact float conversion. |
| N07 / P1 | `encode(decode('a201000001').value,{canonical:true})` returns the original unsorted map. `encode(decode('f82a').value)` emits an ordinary map instead of simple(42). | [useCborCollectionEncoder.ts](../../src/encoder/composables/useCborCollectionEncoder.ts) skips sorting when retained entries exist; [useCborEncoder.ts](../../src/encoder/composables/useCborEncoder.ts) has no dispatch for decoded `{simpleValue}` wrappers. Deterministic mode must override preservation metadata; add an explicit simple-value type and encoder dispatch. |
| N08 / P1 | `81d86481d8648100` bypasses `maxDepth:2` in normal decode, while source-map decode rejects it. `decode('4401020304',{limits:{maxOutputSize:1}})` succeeds. | Collection and tag dispatchers reset each other's recursion counters; output accounting is only partially wired. Carry a shared context through every recursive call, count aggregate work/allocations, and enforce one deadline across sequences and chunk loops. The depth bypass is reproduced; deadline gaps are from code inspection. |
| N09 / P2, completeness | `db0020000000000000f6` rejects tag 9007199254740992, even though its argument is within CBOR's uint64 space. | `TaggedValue.tag`, encoder tag input, and both tag-number parsers use safe JavaScript Numbers. Support `number \| bigint` end to end, including source maps, diagnostics, JSON bridges, and tag lookup. Otherwise publish a clear implementation limit rather than claiming unconstrained generic support. |
| N10 / P1 for advertised validation | `validateTagSemantics:true` accepts tag 24 over an integer (`d81800`) and over malformed embedded CBOR (`d81841ff`). It also accepts a timezone-free tag-0 date and impossible base64url text `d8216141`. | Complete raw tag type/value validation. Use structural parsing for embedded CBOR with shared limits and single-item consumption; improve date/calendar and base64 validation. Opaque preservation remains a useful separate mode. |
| N11 / P1, Cardano layer | Tag 121 is described as an address network tag. Three-element Shelley-style transactions put metadata into `isValid` and leave `auxiliaryData` unset. Conway tag-258 witness collections remain wrappers despite array return types. | Correct [useCardanoCborDecoder.ts](../../src/cardano/composables/useCardanoCborDecoder.ts)'s tag descriptions and [useCardanoHelpers.ts](../../src/cardano/composables/useCardanoHelpers.ts)'s era-specific envelope/witness handling. Normalization of transaction body sets alone was insufficient. |
| N11 / P2, Cardano validation | `d866821b002000000000000080` rejects a uint64 constructor index under Plutus validation. `d879816161` accepts text in a Plutus constructor field. | The constructor checker only accepts Number indices and checks outer array shape, not recursive Plutus Data. Separate annotation from full Plutus validation; preserve large indices and enforce field types and chunk rules in a named Plutus profile. |
| N12 / P2, diagnostics | `fromDiagnostic` rejects `b32'CI2FM6A'` and `h''_`; `simple(42)` cannot re-encode correctly. `decodeToDiagnostic('c24101')` emits `2(1)`, misrepresenting a tag whose content was bytes. Binary16 positive zero renders as integer `0`. | [useCborDiagnostic.ts](../../src/parser/composables/useCborDiagnostic.ts) operates on values that already lost wire type information. Render from a lossless node model, then extend diagnostic parsing. RFC 8949's diagnostic notation is informal; a parser is an extra feature, and the current “complete” claim should be narrowed until supported forms are documented and tested. |

Wire-format references for N01–N10 are [RFC 8949 §§3–5](https://www.rfc-editor.org/rfc/rfc8949.html#section-3), including [deterministic requirements](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1) and [map-key equivalence](https://www.rfc-editor.org/rfc/rfc8949.html#section-5.6.1). Diagnostic forms are described in [§8](https://www.rfc-editor.org/rfc/rfc8949.html#section-8). The table's outputs and root causes come from the local implementation and executed probes.

N05 also includes the verified [erratum 8589](https://www.rfc-editor.org/errata/eid8589): NaN key equivalence takes the sign bit into account. `a2f97e0000f9fe0001` contains opposite-sign NaNs with matching payloads and is rejected as duplicate keys. Keeping only JavaScript Number/Map values loses the information needed to implement that distinction.

Cardano references are pinned [Shelley CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/ae2c8912b204d11e102faeb617b6faa6a8c9f934/eras/shelley/impl/cddl/data/shelley.cddl) and [Conway CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/ae2c8912b204d11e102faeb617b6faa6a8c9f934/eras/conway/impl/cddl/data/conway.cddl). The envelope reproduction is a serialization-shape fixture, not a claim that its empty-input transaction is valid on-chain. These CDDL files also document constructor uint arguments, recursive Plutus Data, and tagged witness lists/sets.

The prior work has useful foundations: all major types, exact 64-bit integers, generic tag preservation within its supported number range, configurable UTF-8/duplicate policies, indefinite values, sequences, source mapping, and separate Cardano helpers. The uint64 endpoints, normal float decoding, malformed simple encodings, strict UTF-8 rejection, and basic indefinite arrays pass the independent control checks.

For the next implementation, I recommend a shared **lossless node representation** containing major type, argument width, original byte span, string chunks, map entries, and tag content. Expose ordinary JavaScript values as a projection. This gives the inspector accurate paths, lets generic and validating APIs share parsing, and supports exact-byte preservation without confusing it with deterministic re-encoding. Floats with integral values, distinct map key types, nonpreferred integers, duplicate entries, and bignum bytes otherwise cannot reliably survive a value-only round trip.

Use explicit profiles: generic inspection; CBOR validity; bytewise deterministic; length-first deterministic; Plutus Data; and era-specific Cardano serialization. Preserve `strict` as a documented compatibility alias during migration. Currently it combines canonical, Cardano, UTF-8, and tag rules; it is not a general definition of “valid Cardano”. In particular, [CIP-21](https://cips.cardano.org/cip/CIP-0021) describes hardware-wallet interoperability restrictions, not every encoding accepted by the Cardano ledger.

After P1 repairs, add optional tag modules in the order in [standards.md](standards.md). Each should report whether it preserves, validates, interprets, and re-encodes a tag. Returning `{tag,value}` is useful generic support, but should not be presented as semantic implementation of the extension.
