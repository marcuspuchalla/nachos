**cbor.app integration audit and release sequence**

The Vue app imports its parser, encoder, diagnostics, and Cardano helpers from the Nachos package. Vite has no alias bypassing that package with an older embedded implementation. This is the right integration shape, but installed dependencies, lockfiles, tests, and display behavior need attention before deployment.

| ID / priority | Finding | Proposed change |
| --- | --- | --- |
| A01 / P1 | [package.json](../../../cbor_decoder/package.json) requests Nachos `^0.4.0`; [package-lock.json](../../../cbor_decoder/package-lock.json) records `^0.3.0` and resolves 0.3.0. Local node_modules contains a 0.4.0 package whose production sources match the Nachos working tree. npm's published latest is 0.3.0. | Test a clean install of the exact reviewed tarball before release; after publication, update the dependency and lockfile together, then test the exact registry artifact. Existing node_modules success does not establish reproducible installation. |
| A02 / P1 | [cborJson.ts](../../../cbor_decoder/src/utils/cborJson.ts) is described as round-trip safe but converts a Map to `{}` and `[undefined,NaN,-0]` to `[null,null,0]`. [cborToJson.ts](../../../cbor_decoder/src/utils/cborToJson.ts) overwrites integer/text key collisions and drops a literal `__proto__` key. | Introduce a typed lossless export format with map entry arrays and explicit simple/float/tag types. Keep ordinary JSON as a clearly labeled display projection. Use safe object construction wherever literal map keys are emitted. |
| A03 / P1 | [useDecoder.ts](../../../cbor_decoder/src/composables/useDecoder.ts) calls the source-map Cardano decoder without validation options. A partial parse of `0102` displays the first item; trailing bytes only trigger an address-fallback attempt. Source-map validation defects therefore reach the main UI. | Offer single-item and sequence modes, display unconsumed bytes explicitly, and expose named validation profiles. Carry options through the Cardano wrapper. Surface validity findings beside the raw tree without losing the user's input. |
| A04 / P1 | [json-test-runner.test.ts](../../../cbor_decoder/src/__tests__/json-test-runner.test.ts) hardcodes `/Users/tk/projects/cbor-cardano-test-suite/tests`, loads 358 older cases, and returns from tests on “out of bounds”/“Insufficient data”. Three such returns were logged while Vitest reported 701 passes. It also uses ineffective option names such as `maxArrayItems` and `maxMapPairs`. | Consume the reviewed TACO corpus by version or project-relative configuration. Make absent required fixtures fail in CI, quarantine known invalid fixtures explicitly, remove exception-to-pass behavior, and type-check test options against `ParseOptions`. |
| A05 / P2 | [useReEncode.ts](../../../cbor_decoder/src/composables/useReEncode.ts) compares bytes after encoding a value projection. Nonpreferred widths, integral floats, source-map map metadata, and original bignum contents can be lost. Exact-byte and semantic differences are presented through one comparison. | Show separate byte and value comparisons. Preserve source nodes for exact re-encoding, and let deterministic output be an explicit operation. Do not infer that a byte mismatch is a decoder failure or silently use altered bytes for Cardano identifiers. |
| A06 / P2 | Decoding and analysis run synchronously on the UI thread. The Cardano decoder has fixed parser options, and diagnostic rendering reparses the input. Library timeout/depth checks are not a browser cancellation mechanism. | Move expensive decoding to a worker, add cancellation and practical input limits, and reuse the parsed tree for diagnostics/analysis. Virtualize large collections. Add a worker smoke test with a bounded stress fixture. |
| A07 / P2 | The UI displays its application version, but not independently verifiable Nachos artifact identity. The public site's entry bundle differs from the current local build, and a cached PWA can outlive a deployment. | Include actual build/library version and source/artifact identity in an About/debug view. Verify service-worker upgrade behavior and the served version after deployment. |

The public [cbor.app](https://cbor.app/) returned HTTP 200, with entry asset `/assets/index-BSgHYIEy.js`. The local checked build emitted `/assets/index-BIhDURfR.js`. This confirms that the checked local build and the public entry artifact differ; it does **not** identify the exact Nachos version used by the public site. No browser interaction test, deployment, or service-worker migration was performed during this audit.

Validation used Node 24.13.1: Vue type-check, Vite/PWA production build, and 22 test files passed. Vitest reported 701 passes, with the three false-pass returns noted above. The original shell-selected Node 16 failed before test startup; that environment issue was resolved for verification by selecting the already installed Node 24. Pin the intended runtime in this repository so normal commands and CI agree.

**Proposed release sequence, with publication awaiting your acknowledgment**

1. Repair the Nachos P1 findings and add focused regressions. Keep its earlier July work intact and reconcile the changelog's completeness claims with measured support. Complete current-source tests, TypeScript, both builds, and package export checks.
2. Repair TACO's comparison/oracle/generator issues. Put the Nachos candidate tarball into an isolated test environment and test normal/source-map/byte-input paths. Run the broad ecosystem matrix using pinned versions; preserve results and provenance without updating public rankings prematurely.
3. Exercise the same candidate tarball in a clean app install, including the malformed strings, bignums, mixed keys, sequences/trailing bytes, generic CBOR examples, and representative Cardano fixtures. Verify browser UI, worker behavior if added, and PWA update flow locally.
4. Present the final candidate version, changelog, package contents, and verification results for acknowledgment. `0.4.0` is currently staged locally and unpublished; choose the release number against the public 0.3.0 baseline and the final API changes, rather than assuming another release already occurred.
5. After acknowledgment, publish Nachos. Verify its registry metadata, integrity, ESM/CommonJS imports, and installed behavior. Update TACO's exact package pin, lockfile, and runtime version reporting, then regenerate reviewed reports.
6. Update the app dependency and lockfile to that published version, run a clean install/build/tests and browser smoke checks, deploy, and verify the served library identity and service-worker upgrade.

This sequence makes acknowledgment a review of a concrete release candidate. The present deliverable is the audit and evidence; production fixes, a new npm publication, new ecosystem rankings, and deployment remain proposed work.
