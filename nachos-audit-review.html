The headline

NACHOS decodes the RFC 8949 data model correctly and linearly, with an unusually thorough DoS-limit story and strict UTF-8 handling. The gaps are at the determinism & well-formedness boundary: the canonical ordering follows the older length-first rule, one parse path skips a depth guard, and a float16 gate is mis-bounded.

Update All findings remediated

Every finding (H1–L5) is now fixed, verified empirically, and locked in by 24 regression tests — full suite 1339/1339 green. H2 was reframed after research: length-first is the correct Cardano CIP-21 default; a mapKeyOrder option now also offers RFC 8949 §4.2.1.

Round 3 · Security

02Two parse paths, two security postures

HighH1 Stack-overflow DoS in decodeWithSourceMap()
parseTagFromBuffer (the decode() path) enforces maxTagDepth via RUSTSEC-2019-0025 mitigation. But parseTagWithMap (the source-map path) recurses with no tag-depth or recursion guard — only a wall-clock timeout that a stack overflow beats. A hostile c2 c2 c2 … stream crashes the process with an uncatchable-by-default RangeError instead of a clean error.
$ node — decode vs decodeWithSourceMap, input = 0xc2 ×60000 + 0x00 decode(…, {maxTagDepth:100}) → Error: Tag nesting depth 100 exceeds limit of 100 ✓ clean decodeWithSourceMap(…, {maxTagDepth:100}) → RangeError: Maximum call stack size exceeded ✗ crash

Fix: thread the same depth counter + limit checks through parseValueWithMap / parseTagWithMap. Both paths should share one well-formedness guard.

Round 1 · Determinism · RESOLVED

03"Canonical" ordering — the research changed the verdict

ResolvedH2 Length-first is correct for Cardano — the gap was a missing option
Cardano CIP-21 (transaction serialization) mandates RFC 7049 §3.9 "Old Canonical CBOR" — length-first ordering: "keys sorted from lowest value to highest," shorter first, ties bytewise. So NACHOS's existing length-first order is right for its flagship use case — not a bug. The real defect was narrower: an RFC 8949-branded library with no way to get §4.2.1 bytewise order, and an ambiguous "canonical".
$ FIX — explicit mapKeyOrder option, both encoder & decoder encodeToHex(m,{canonical:true}) = a2 626161 01 1a000f4240 02 (length-first, CIP-21 default) encodeToHex(m,{canonical:true,mapKeyOrder:'bytewise'}) = a2 1a000f4240 02 626161 01 (RFC 8949 §4.2.1) decode(…,{validateCanonical:true,mapKeyOrder:'bytewise'}) ⇄ enforces matching order on both sides

Shipped: default stays length-first (CIP-21, backward-compatible); new mapKeyOrder: 'length-first' | 'bytewise' exposes RFC 8949 §4.2.1. Plutus Data maps preserve order — use non-canonical mode. Sources: CIP-21 · RFC 7049 §3.9 · RFC 8949 §4.2.1

Round 2 · Correctness

04The float16 gate the encoder fails against itself

MediumM5 canBeFloat16 uses the wrong lower bound (min-normal, not min-subnormal)
The encoder's float16 gate rejects anything below 0.00006103515625 = 2⁻¹⁴ (smallest normal half), but float16 subnormals reach down to 2⁻²⁴. So encode(2⁻²⁴) emits a float32 — which the decoder's own fitsInFloat16 (correctly bounded at 2⁻²⁴) then rejects as non-canonical. The encoder produces output its own canonical validator won't accept. encodeFloat16Bytes itself handles subnormals — only the gate is mis-bounded.
$ v = 5.960464477539063e-8 (= 2^-24, smallest float16 subnormal) encodeToHex(v) = fa 33800000 (float32 — should be float16) decode("fa33800000",{validateCanonical:true}) → REJECTED: "value fits in float16, use shortest"

Fix: drop the lower-bound short-circuit and rely on the encode→decode equality check already present, or set the bound to 2⁻²⁴. Add a round-trip property test: every encoder float output must pass validateCanonical.

Round 2/3 · Correctness & robustness

05Three more medium findings

MediumM1 decode() silently ignores trailing bytes
A single decode of 000102 returns {value:0, bytesRead:1} and drops two bytes. bytesRead lets callers detect it, but there's no strict whole-input mode that rejects extraneous data.
MediumM2 Encoder maxDepth not enforced across tag boundaries
Tagged-value encoding re-enters via the top-level encode, resetting ctx.depth to 0. 300 nested {tag,value} objects encode cleanly despite a default limit of 64 — a stack-overflow vector with no clean error.
MediumM3 Duplicate map keys silently collapse
Default dupMapKeyMode:'allow' stores into a JS Map, so duplicate keys keep only the last value — silent data loss. 'reject'/'warn' exist; default should warn or preserve via ALL_ENTRIES.
MediumM4 Canonical mode accepts non-shortest tag numbers
decode("d80100",{validateCanonical:true}) is accepted — tag 1 in 1-byte form — though the shortest form is c100. Shortest-form is enforced for ints/lengths/floats but not for tag numbers (or simple values).
Lower-priority & hygiene

06Low-severity findings

  • L1 · parseSequenceWithSourceMap re-slices the buffer from each item's offset to the end → O(N²) over long sequences. Debug-only path, but unbounded.
  • L2 · dispatchFromBuffer converts buffer→hex for array/map/tag dispatch — an extra full-slice allocation (not O(N²), but avoidable now that sub-parsers are buffer-native).
  • L3 · readUint accepts up to 8 bytes using *256 float math (precision loss > 2⁵³). Latent only — callers cap it at ≤4 bytes today.
  • L4 · Plain-object map keys are string-coerced and reordered by the JS engine's integer-index rule. By design (docs steer users to Map) — worth a louder warning.
  • L5 · Diagnostic notation is partial: fromDiagnostic is a stub, and emitted notation lacks indefinite markers / typed annotations for decoded values.
Credit where due

07What NACHOS already does well

Verified Linear decoding

Buffer-native sub-parsers; ~0.4 µs/element flat from 50k→400k. The old O(N²) is gone.

Verified Deep DoS-limit story

Input, output, string, array, map, depth, tag-depth, bignum and parse-time limits — all configurable, all enforced on the decode() path.

Verified Strict UTF-8

Rejects overlong encodings, surrogate code points, >U+10FFFF and bad continuation bytes.

Verified CVE-aware

Bignum byte-cap (CVE-2020-28491) and tag-depth cap (RUSTSEC-2019-0025) baked in.

Verified Round-trip fidelity

Indefinite-length + chunk preservation via symbols; shortest-form checks for ints/floats/lengths; canonical NaN enforcement.

Verified Clean packaging

Zero dependencies, dual ESM/CJS, full types, source maps, and a broad test suite (40+ spec files).

The plan

08Remediation roadmap

P0 · CORRECTNESS & SECURITY

Ship before next release ✓

  1. H1 — share the depth/tag-depth guard with the source-map parse path (kill the stack-overflow).
  2. M5 — fix the float16 lower bound; add an "encoder output is self-canonical" property test.
  3. M2 — thread maxDepth through tagged-value encoding.
P1 · CONFORMANCE

Determinism & well-formedness ✓

  1. H2 — add §4.2.1 bytewise ordering as default; expose mapKeyOrder option.
  2. M1 — strict whole-input mode (decodeFirst vs decode) rejecting trailing data.
  3. M4 — enforce shortest-form tag numbers + simple values under validateCanonical.
  4. M3 — default dup-key mode to warn, or preserve all entries on decode.
P2 · QUALITY

Polish & assurance ✓

  1. L1/L2 — drop buffer→hex round-trips; buffer-native sequence source maps.
  2. L5 — complete diagnostic notation + fromDiagnostic.
  3. Add RFC 8949 Appendix A vectors as a CI gate + fuzz/round-trip property tests.
  4. L3/L4 — harden readUint; louder plain-object key warning.
